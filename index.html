I write software, and I care about the quiet parts of it: clear names, good documentation, and a second draft.

I treat software as an engineering discipline. Work in small steps, get feedback fast, and let evidence decide what ships. I would rather learn in an afternoon that an idea is wrong than defend it for a quarter.

That is why I start from behaviour. I write down what a system should do, in plain language and worked examples, before deciding how it will do it. The specification becomes the first draft of the design, the tests become its proof, and the code has something to answer to.
